# Agent Note: 全局同步、托盘与自启收尾（多实例吸附专题工单 04）

Status: implemented

## Problem

专题收口票：01–03 给了实例身份、松手吸附与组联动，但全局设置改
一处不达其他实例、托盘无编号不可辨识、没有开新实例 / 退出全部的
入口、自启只拉起 1 号一扇。本票补齐全局同步轮询、托盘编号与菜单、
设置窗编号标题、在运行标记与自启恢复，并汇总全专题实机清单、收
口文档（README、仓库外需求文档、GLOSSARY / ADR-0004 校对、spec
注记）。

## Decision

- 全局同步（新库 module `global_sync`，纯判定可测）：
  - `GlobalSettings` 是全局段快照（recursive / playback / display /
    general 的同步相关键；续播状态不入快照——它随每次切图落盘，
    入快照会让轮询被自己的显示流程顶着空转比对）。`GlobalSyncState`
    状态机记上次修改时间与上次应用快照：mtime 未变不发信号；变了
    才重读；重读值与已应用值相同（对方只写了自己的实例段）返回
    None，不重复应用。
  - 只读重读在 `ConfigStore::reload_globals`：重读磁盘、只把全局
    段换进内存视图，实例段与实例段快照一律不碰，永不写回（盘上
    修复只在内存副本上做）。`ConfigSync` 只做装配透传。
  - 宿主应用（`FrameApp::poll_global_sync`）：只应用宿主 / 核心持
    有的那部分——外观、内置画框、相框图路径、窗口吸附开关（副作
    用与设置窗路径共用 `apply_window_snap_value`，含工单 03 的停
    摆 / 武装）、核心播放三项（模式 / 间隔 / 动画经既有意图改值，
    其 Save 系列效果逐项滤除——同步绝不触发写回，对方已经写过
    了）。autostart 以注册表为准、续播状态归各自显示流程，都不
    在同步应用之列。
  - 轮询成本口径（定死，与工单 03 协调）：同步不新增任何定时器
    或唤醒；宿主只在既有调度已唤醒的帧上 stat 一次修改时间（多
    实例时工单 03 的跟随心跳 1000ms 帧天然承载，同步延迟约一个
    心跳周期；单实例静止时靠 incidental 帧），不把静止零重绘顶
    成常开。已写进 spec 第 14 节注记。
- 在运行标记：实例段新增 `running` 键（`InstanceConfig.running`，
  缺失 / 非法按 false 修复），置位 / 清除走工单 01 的写入纪律通
  道（`ConfigStore::set_instance_running` 只改本实例段一个键）；
  置位在 run() 启动装配后，清除在 Effect::Exit 落地处（一切正常
  退出路径的汇合点），崩溃残留不清。
- 自启恢复（协调者定死口径，原样执行）：**任何 1 号实例启动时都
  尝试恢复**（不区分自启 / 手动启动），且必须幂等——只拉起「实
  例段有在运行标记、且该编号当前没有活进程持有锁」的编号：纯裁
  决 `instance::recovery_targets` 以实例段标记 + `lock_holder_pid`
  读到的锁持有者 pid + 工单 01 的 `process_alive` 接缝区分崩溃残
  留（有标记、锁已失效 / 持有者已死 → 拉起）与真在运行（锁被活
  进程持有 → 绝不重复拉起）。拉起的新进程经命令行 `--instance
  <编号>` 走受控的指定编号认领 `claim_specific_instance`（与最小
  空缺认领共用同一套锁纪律：create_new 原子占位、陈旧锁回收；
  被活进程持有返回 AlreadyExists，子进程据此安静退出），回到各
  自落盘位置（几何恢复归工单 01 口径）。spec 第 10 节原句「不做
  存活探测、残留会多拉一扇」与此口径有出入，已按「只加注记段」
  规则在 spec 第 14 节补注记取代，未改定案正文。
- 托盘（菜单顺序与命名定死）：tooltip「萌框 · 相框 N」；菜单自上
  而下为：关闭相框 / 显示相框、暂停 / 播放、分隔线、上一张、下一
  张、分隔线、设置、新建相框、分隔线、退出、退出全部相框。「新
  建相框」拉起新进程认领最小空缺编号（与再次运行 exe 同效果）。
  「退出全部相框」：先经工单 02 的枚举给全部伙伴相框窗（含隐藏
  到托盘的）发退出请求，本实例最后退出。
  - 退出请求的落地形态（spec 第 14 节补注）：裸 WM_CLOSE 会被
    接收方的「关闭即隐藏」拦成隐藏，故发起方先在伙伴窗上置窗
    口属性 `MoeFrame.ExitAllRequested` 再投递 WM_CLOSE，接收方
    每帧读到属性才走自身正常退出路径（Intent::ExitRequested：
    清标记、几何冲刷、摘托盘）；普通关闭无属性、不受影响。全
    程是窗口枚举 + 窗口消息 / 属性，不建 IPC。
- 相框右键菜单最终形态（定死，守菜单瘦身口径，本专题只加了工单
  03 的「脱离吸附组」一项，本票不加项）：上一张 / 下一张 / 播放
  ·暂停 / 脱离吸附组（仅当前有直接接触时出现）/ 置于顶层 / 置于
  底层 / 设置 / 退出——共 7 项、无接触时 6 项。「退出」只退本实
  例，与托盘「退出全部相框」文案分工不混淆。
- 设置窗标题「萌框设置 · 相框 N」（FrameApp 新增 instance_number
  字段自 HostInit 读入）；相框窗标题保持 `MoeFrame` 不变。
- 编号释放复用：沿工单 01 认领口径，本票以「退出释放 → 新建相
  框认领最小空缺」的端到端场景列入实机清单复验（认领 / 释放的
  自动化覆盖在工单 01 与本票指定认领测试里）。

## Alternatives considered

- 同步应用核心播放三项时新开核心的无保存意图：要改 app_core 的
  意图面；现方案复用既有意图、在宿主分发前滤除 Save 效果，行
  为副作用（间隔重计等）与本地改值一致、落盘面为零——不采纳
  新意图。
- 退出全部只发裸 WM_CLOSE：接收方必然被关闭即隐藏拦下，只会
  把伙伴藏进托盘而不是退出，与 spec「各实例走自身正常退出路
  径」不符——改为窗口属性 + WM_CLOSE（见 Decision）。
- 自启恢复只认自启启动：进程无法可靠区分自己是被自启还是被手
  动拉起，且协调者已定死「任何 1 号启动都恢复」——不做区分，
  靠标记 + 锁存活保证幂等。
- 同步轮询加独立低频定时器（如 1s）：会把静止零重绘顶成常开，
  违反 spec 第 12 节稳态口径——不采纳，骑既有唤醒帧。

## Consequences

- 全局设置一处修改全家实时生效（约一个跟随心跳周期内）；多开
  时托盘 / 设置窗可按编号辨识；自启能恢复上次在运行的全部相框
  且不重复拉起。
- 遗留风险：(1) 宿主层（托盘菜单、退出属性通路、恢复拉起、同步
  应用）未实机验证，全部列入 real-machine-check-multi-instance-
  snap.md（31 条）待用户真机逐项验。(2) 单实例且完全静止（无伙
  伴、无任何唤醒帧）时，同步要等下一次 incidental 帧才落地——
  这是零重绘口径下的既定取舍，多实例场景由跟随心跳兜住延迟。
  (3) 退出属性以窗口属性名为约定：同名属性被其他程序误置的理
  论风险极低（属性只置于已通过标题 + exe 双层校验的伙伴窗与自
  窗）。(4) `--instance` 指定认领与正常启动并发同一编号时，败者
  安静退出，观感上像「双击没反应」——只发生在恢复拉起与用户手
  动启动精确撞号的极窄窗口。
- 实机 31 项未验，本票 Status 置 needs-info。
