# Agent Note: 顺序轮播的计时只认行为核心里的截止时刻

Status: implemented

## Problem

[工单 11](../../../../.scratch/v1-exe/issues/11-sequential-slideshow.md) 要在工单 10 的行为接缝上加顺序浏览与定时轮播：手动切换要重计满间隔、暂停只停自动切换、间隔改值与同值的处理不同、加载失败不能算成功切换。若计时散落在宿主的 UI 回调里，这些规则无法用可控时间验证；若导航在加载期间被简单丢弃，慢解码时用户的连续按键会丢输入。

## Decision

- 新增纯逻辑 `playlist`（播放序列）：持有扫描给出的完整路径自然序与当前位置，提供循环的紧邻下一张与按方向的轮转候选（不含当前图）。命名说明：英文标识 `Playlist` 沿用父规格 Testing Decisions 对这条接缝的称呼；中文一律用词汇表的「播放序列」，不用其 Avoid 的「播放列表」。
- 计时全部收进行为核心：核心只持有一个截止时刻（`deadline_ms`），时间由意图携带的单调毫秒推进，宿主取 UI 时钟并睡到截止时刻才唤醒重绘。成功切换（首图与导航同一路径）在完成时刻计满；手动失败不重置；自动失败隔满一个间隔再试；暂停清截止、恢复时从恢复时刻计满；改间隔从生效时刻重计，同值不重计也不重写。
- 加载在飞时的手动导航只保留最后一个排队，加载收尾后接着执行；Tick 在飞时不触发。在飞期间改间隔且导航最终失败的组合，靠 `recount_on_settle` 标记在收尾时按新间隔补计——这是审查发现的真实缺口，初版会漏计。
- 预加载落在工作线程的单份缓存：核心在每次成功显示后发出 `Preload` 效果指向紧邻下一张；工作线程按路径 + 物理目标 + 显示模式键控缓存，正式加载首候选命中即交出，扫描新文件夹时清空。长期只多留这一份显示数据。
- 本票只实现顺序模式：配置的播放模式键（默认 `random`）只保存，核心无条件顺序，随机与历史由工单 12 接入——此立场已写进 `app_core` 模块文档与工单 11 的 Comment，避免「配置写随机、行为是顺序」成为隐形状态。

## Alternatives considered

- **宿主用 egui 计时器直接驱动轮播** — 代码更少；但手动重计、暂停恢复、失败不提交等规则会散进 UI 回调且无法可控推进验证，因此拒绝，宿主只负责送 Tick 与按截止时刻安排唤醒。
- **导航在飞时直接丢弃** — 初版如此；审查指出慢解码下连续按键会丢输入，改为只留最后一个排队意图，语义与父规格动画票的「保留最后意图」方向一致，且不引入队列复杂度。

## Testing

- 全量测试通过（本票新增：playlist 6 项、行为核心 12 项、config 间隔保存 1 项），时间全部由意图的 `now_ms` 推进，无真实等待。覆盖：到点触发与未到点不触发、手动重计、暂停中手动切换、恢复计满、改间隔重计与同值不动、暂停中改间隔只记录、手动失败保留当前图与原截止、自动失败隔间隔重试、单图不自转、在飞排队导航收尾执行、在飞改间隔后失败补计。
- Windows 目标 `cargo check --all-targets`、clippy、`cargo fmt --check` 通过。
- 双轴审查（基线 `691d84a`）已处理：Spec 轴的在飞改间隔失败漏计、在飞导航丢弃、播放模式立场不可见三项已修或已明文记录；Standards 轴的中文术语已改「播放序列」、滚轮阈值已命名常量。未改两项判断项：`now_ms` 随四个意图变体传递（形状一致、可读，包一层时间戳意图的收益不足）、配置 setter 的文档编辑形状重复（模块既有惯例，第二个实例不抽取）。
- 未验证：方向键、空格、滚轮与菜单在真实窗口中的触发，以及预加载命中的实际切换观感，需 Windows 实机记录；本票因此转 `needs-info`，不标 resolved。

## Consequences

- 工单 12 的随机与历史应继续落在播放序列与行为核心内：随机决定「下一个候选是谁」，计时与失败语义不需再动。工单 14 的动画接入时，在飞排队规则需与动画的保留最后意图规则对齐复核。
- 宿主从此每帧送 Tick 并按核心截止时刻安排唤醒；后续任何新的时间相关行为都应先问核心要截止时刻，不在宿主另建计时器。
