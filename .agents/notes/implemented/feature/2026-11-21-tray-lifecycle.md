# Agent Note: 关闭与退出在核心里就是两个意图，托盘只是又一个输入源

Status: implemented

## Problem

[工单 17](../../../../.scratch/v1-exe/issues/17-tray-lifecycle.md) 要托盘常驻：关闭相框（含 Alt+F4）只隐藏、进程与轮播继续，托盘左键与右键菜单能找回相框、控制播放与导航，只有明确选择退出才结束进程。此前宿主对窗口关闭没有任何拦截——egui 收到关闭请求就关窗退进程，「关闭」与「退出」在实现里是同一件事，与词汇表的定义（关闭=只隐藏、退出=结束进程且只能由菜单或托盘明确选择）正相反。另一个结构性问题是：若托盘在宿主里自带一份播放状态或直接操作窗口，隐藏期间的轮播、历史与落盘就会与相框本体分叉。

## Decision

- 核心新增可见性状态与三个既有概念的对齐：`Intent::CloseRequested` 只产出 `Effect::HideFrame`（不动播放状态、当前图与轮播截止时刻，隐藏中重复关闭是无动作）；`Intent::ToggleVisibilityRequested` 翻转可见性并产出 `ShowFrame`/`HideFrame`；结束进程仍只有原有的 `ExitRequested → Effect::Exit` 一条路。可见性经 `frame_visible()` 只读暴露，宿主不自存一份。
- 托盘是纯输入源：宿主每帧轮询 tray-icon 与 muda 的事件接收器，左键单击（只认抬起沿，一次点击只切换一次）映射 ToggleVisibilityRequested，菜单项（关闭/显示相框、暂停/播放、上一张、下一张、退出）映射与相框菜单完全相同的核心意图——隐藏期间同样有效，不存在第二份播放状态或历史；隐藏期间成功显示的提交与落盘走原有路径（SaveResumeState），唤回看到的就是实际当前图。
- 宿主关闭拦截：每帧读 `close_requested()`，非退出状态下同帧 `CancelClose` 并转发 CloseRequested；明确退出时先置 `exiting`、摘掉托盘图标再发 Close，关窗即结束。托盘首帧在事件循环内懒建（tray-icon 需要消息泵），建失败降级为无托盘，相框本体照常运行。
- 隐藏心跳：托盘事件靠 ui() 轮询，而暂停且隐藏时核心没有轮播截止时刻、宿主原本不安排任何唤醒——唤回点击可能无人处理。宿主在相框隐藏期间固定以 250ms 请求重绘作为心跳，托盘事件最迟在一个心跳内被处理；轮播 Tick 仍按自身截止时刻在帧上判定，播放中隐藏的推进节奏不变。可见时不启用心跳，不增加空转。
- 托盘菜单不含「设置」：工单 18 才接入设置窗，本票按工单 Context 不摆无效入口。图标按需求文档 §8.3 用内置 PNG（assets/tray-icon.png，编译时嵌入、image 解码为 RGBA），不过程绘制。`tray-icon = "=0.21.3"` 门控在 `[target.'cfg(windows)'.dependencies]`，不让 Linux/macOS 的传递依赖进锁文件主体。托盘文案的初始值与同步都从核心现读（tray_state 以 None 起步，首帧必同步），核心默认值变化不会让文案失同步。

## Alternatives considered

- **宿主直接 Visible(false) 处理关闭、不经核心** — 少两个意图；但工单验收标准 7 明确要求行为测试覆盖关闭与退出分离、隐藏时轮播与导航，宿主直处理无法测，且可见性状态会散在宿主与核心两处，因此拒绝。
- **托盘事件用回调直接操作窗口/播放** — 延迟最低；但回调绕过行为入口等于第二份状态机，隐藏轮播与历史必然分叉，因此拒绝，托盘只产意图。
- **隐藏时完全依赖系统消息唤醒帧循环** — 省掉心跳的 4 次/秒空帧；但暂停+隐藏时没有任何代码能证明帧会跑（Spec 审查点名），而心跳成本可忽略，因此拒绝，把确定性买回来；可见时仍按截止时刻长睡。

## Testing

- 全量测试 146 项全绿（本票新增 4 项行为测试）：关闭只隐藏不退出且播放/当前图不动、重复关闭无动作、明确退出仍有效；切换交替产出显示/隐藏效果且不重复建任何东西（核心层）；隐藏期间到点自动轮播并提交落盘、手动导航有效、唤回后当前图为实际推进后的图；隐藏中暂停后 Tick 无动作。
- Windows 目标 `cargo check --all-targets`、clippy 通过（仅余工单 09 验证程序的 3 个既有警告）；`cargo fmt` 已应用。
- 双轴审查（基线 `61e5512`）：Standards 轴无硬违规（词汇表关闭/退出分离、ADR-0002/0003、§8.3 精确版本钉都成立），判断项处置：tray-icon 改 Windows 目标门控；托盘文案改用词汇表动作名「关闭相框」（内部 Hide/Show 标识对应 egui Visible 命令语义，保留）；图标改内置 PNG 合 §8.3 原文；托盘初始状态改从核心现读；意图映射与相框菜单并行一份属结构性重复（muda 与 egui 两套 API），记录不改。Spec 轴无缺失、无蔓延；点名的唯一真实风险——暂停且隐藏时无唤醒、托盘输入可能睡死——已用隐藏心跳关闭，并把「暂停→隐藏→托盘唤回」与「隐藏状态下从托盘退出」列为实机清单的必查项。
- 未验证：托盘图标实际出现、左键/右键手感、Alt+F4 拦截、隐藏唤醒时延、隐藏中从托盘退出——工单验收标准 8 明确要求实机执行人验证且 mock 不算数，已并入合并实机清单（工单 10–17），本票因此转 `needs-info`，不标 resolved。

## Consequences

- 工单 18 的设置窗从托盘打开时，在 `build_tray` 的菜单里补「设置」一项并映射一个新意图即可；注意工单 17 准则 6：显示/隐藏相框与打开/关闭设置窗是两套独立生命周期，不要把设置窗挂到可见性状态上。
- 隐藏心跳意味着隐藏期间进程每 250ms 醒一次：工单 22/23 做资源预算验收时，隐藏状态的 CPU 占用应按这个心跳口径测量，不要按「完全休眠」预期。
- 退出路径没有单独的「退出前保存」步骤：落盘是每次成功显示提交时增量完成的，任何未来的退出前确认/保存需求都要先回答「未提交的在飞显示怎么办」，不要在 Effect::Exit 臂里临时加保存。
