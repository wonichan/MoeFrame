# Agent Note: 跨启动恢复只认成功显示时落盘的三份路径状态

Status: implemented

## Problem

[工单 13](../../../../.scratch/v1-exe/issues/13-resume-state.md) 要让相框重启后先恢复上次当前图、随机模式继续只抽本轮未看图、上一张仍能按历史回看。难点在三份状态的提交时机与损坏隔离：若恢复显示被重复记账，历史尾部会凭空多一条；若当前图已不在图库，随机与顺序的首图规则不同（随机清进度开新轮、顺序取自然序后继）；若三个字段共用一套校验，一个坏字段会把其他合法状态一并清空——工单 02 的十条决定与父规格 §3/§7 都对此有明确规则。

## Decision

- 配置 `[general]` 分区新增 `round_seen`（本轮进度）与 `history`（最近 512 条）两个路径数组字段，与既有 `current_image` 并列；父规格 §7 明确不臆定新增字段名称，表示由实现定。洗牌袋从不落盘（ADR-0002）。三字段在每次成功显示时由 `save_resume_state` 一并写入——同属一次成功显示的提交，预加载与失败不触发。
- 字段级修复沿用 §7 语义：`repair_path_list` 校验「必须是字符串数组」，不合者整字段丢弃并按缺失处理，不牵连其他字段；历史超 512 条在保存与修复两条路径共用 `keep_newest_history` 只留最新。当前图字段缺失/损坏即按缺失处理，不拿历史尾部冒充（工单 02 决定 10）——初版曾做尾部回退，Spec 审查指出其无规格依据，已删除。
- 播放序列 `restored` 接收显式当前图：仍在图库时经 `land_restored` 只落位不记账（恢复是防重复例外），游标停在它在历史中的最后位置；当前图不在历史中时游标停在最新端之外（Some(len)），上一张可回看整段历史。本轮进度按当前图库过滤，历史原样保留、回看跳过缺失路径。
- 行为核心在首次扫描消费 `ResumeData`：当前图在库 → 首候选就是它，失败才按模式继续找；随机当前图缺失 → 清空旧本轮进度、袋从全图库重建；顺序当前图缺失 → 经图库模块的自然序后继位置绕一圈找（顺序比较的唯一实现留在 library，核心不复制排序规则）。用户改选文件夹时恢复数据作废，不当作重启恢复。

## Alternatives considered

- **恢复时把当前图也走一遍新鲜记账** — 代码最省；但历史会重复追加同一张、本轮进度语义被污染，违反工单 02 决定 1/6，因此拒绝，单独设 `land_restored` 落位路径。
- **当前图字段缺失时用历史尾部顶替** — 用户体验上「看起来连续」；但工单 02 决定 10 明确损坏字段按缺失处理，顶替是无依据的发明规则，Spec 审查亦如此认定，因此拒绝。
- **三份状态分开三次保存** — 字段独立性看似更好；但三者同属一次成功显示的提交，分开写会在崩溃时留下互相矛盾的组合（新当前图配旧进度），一并写更接近原子提交，因此拒绝。

## Testing

- 全量测试 114 项全绿（本票新增 13 项）。播放序列恢复测试 5 项：显式当前图的历史游标位置、当前图不在历史时整段可回看、当前图缺失不落位、当前图字段缺失不落位、恢复落位不记账。配置测试 3 项：三字段跨两次加载往返、坏字段各自丢弃不牵连、600 条历史截断到最新 512。行为测试 5 项：随机恢复当前图并续抽未看、随机缺失当前图开新轮、顺序恢复位置且不重复记账、顺序缺失取自然序后继、跨两次启动的完整续播。
- 既有 6 项行为测试因每次成功显示新增 `SaveResumeState` 效果而更新断言（效果序列尾部多一项落盘），行为本身不变。
- Windows 目标 `cargo check --all-targets`、clippy 通过（仅余工单 09 验证程序的 3 个既有警告）；`cargo fmt` 已应用。
- 双轴审查（基线 `637e730`）：Spec 轴一项发现已修正——当前图字段缺失时的历史尾部回退无规格依据，改为按缺失处理并改测试；其余十条决定逐条核对无误。Standards 轴无硬违规；判断项处置：历史 512 截断抽出共用函数（保存/修复两处），宿主路径转字符串抽出小工具；保留两项并记理由——`(current, seen, history)` 三元组在配置层不另立类型（配置不能反向依赖行为核心的 `ResumeData`，再立同构类型只会增加转换）、`ScanCompleted` 的恢复决策树保留在扫描臂内（线性且注释完整，拆分会把 pending/restore_target 的写入散到多处）。
- 未验证：真实退出再启动的恢复观感、配置文件手改后的重启生效，需 Windows 实机记录；与工单 10/11/12 的实机清单合并确认，本票因此转 `needs-info`，不标 resolved。

## Consequences

- 工单 16（手动重新扫描）接入时注意：扫描完成臂现在区分「启动恢复」与「普通重扫」，重扫不得消费或伪造恢复状态；图库增删的进度剔除规则（父规格 §3）落在同一臂上，须与恢复分支分开验证。
- 配置文件从此由程序在每次成功显示时重写 `[general]` 三键；用户手改这三键只在重启时生效（不监视文件），与既有「手改按重启生效」口径一致。
