# Agent Note: 发布资源门有了可复现的测量

Status: implemented

## Problem

`v1-exe` 的 NFR 有三条硬预算（体积 ≤15MB、冷启动 <1s、静止工作集 ≤50MB、静止 CPU <1%），但仓库里没有任何测量手段：没有脚本、没有记录、没有基线。预算从写下那天起就没被验证过一次——不是没达标，是没人知道。

首版脚本跑出来的数字极差：冷启动 2833/5207ms、工作集 151.68/156.66MB、单图库 CPU 5.47%。两份对照还互相矛盾（14 张 1080p–4K 与单张 512×512 的工作集、启动耗时几乎相同），当时误判为"进程基线""启动卡在进程外"。

真实原因在脚本自己身上：脚本把临时配置写到 `<tmp-appdata>\config.toml`，而程序读的是 `<tmp-appdata>\MoeFrame\config.toml`（`app_directory()` = `%APPDATA%\MoeFrame`）。于是每次测量都跑在"没有图片文件夹"的状态，首帧同步弹出文件夹选择对话框（`Effect::PickFolder` → `rfd`），主线程被模态框挡住 1–5s（偶发 45s），对话框拉起的 COM/Shell 又让工作集多出约 75MB。

## Decision

- **`scripts/measure-release.ps1`** 是唯一的资源测量入口：`-GenerateSamples` 生成样本；启动+静止测 `LaunchMs`/`WorkingSetMB`/`PeakWorkingSetMB`/`CpuPercent`；`-SoakMinutes N` 做连续轮播看是否持续增长；`-WithTenThousand` 测万图库。
- **临时 `APPDATA` 下配置必须写到 `<appdata>\MoeFrame\config.toml`**（与 `app_directory()` 一致），`MoeFrame` 目录预建好，测完即弃。
- 产品侧只加**只写日志、不参与行为**的 `[startup]` 标记，且每条自带 `ws_mb`（`GetProcessMemoryInfo`）：`launch`、`app-created`、`first-frame`、`first-image`。这样一次启动既拿到时间也拿到各阶段工作集，不必靠外部采样猜阶段。
- 归因用**内存探针**：`probe_start/probe_mark/probe_dump` 把 `Instant` 记在 `thread_local`，首帧结束一次性落盘。逐点开合日志文件本身能贡献 1–5s 的假停顿，探针代码用完即删。

## 修正后的实测（同一台机器、同一个 exe）

| 项 | 值 | 目标 | 判定 |
| --- | --- | --- | --- |
| 体积 | 7.48 MB | ≤15MB | ✓ |
| 冷启动到首张图 | 282 ms | <1s | ✓ |
| 静止稳态工作集 | 67.79 MB | ≤50MB | ✗ |
| 静止平均 CPU | 0% | <1% | ✓ |

工作集归因（进程内标记）：`launch` 8MB → `app-created` 55MB → `first-frame` 57MB → 描一张小图后 64–68MB。55MB 在窗口 + GL 上下文 + egui 上下文建好后就已经在了。

对照实验：用同一份 `Cargo.toml` 依赖集、同一个 Glow 渲染器、480×320 无边框的空 eframe 窗口（`target/memprobe`，临时工程）稳态 **65.7MB WS / 63.5MB private**，与本程序相差在噪声内 → 工作集由框架底座决定，本项目自有状态只占 2–3MB。

## Alternatives considered

- **在 CI 里跑资源门** — 最强理由：唯一强制的门。否决：需要交互式桌面（窗口、托盘、前台焦点），`windows-latest` 的 session 0 跑不了，启动耗时在共享 runner 上也没有可比性。
- **只靠外部采样（`Get-Process` 定时轮询）** — 否决：看不到阶段，也被上次的污染骗过一次；必须配合进程内标记才能自证"测的是对的状态"。
- **用 `perfview`/ETW 做第一次归因** — 最强理由：能直接看到阻塞来源。否决（暂时）：需要额外工具与符号；先用标记把"到底是哪一段"答掉，成本更低。
- **把探针留在产品代码里常驻** — 否决：`thread_local` + 每帧分支是给归因用的，常驻只会变成新的噪声源。

## Consequences

- 三条预算从"没人知道"变成"知道差多少"：启动与 CPU 达标，工作集 67.79MB 超 50MB，而空窗口底座就有 65.7MB → **≤50MB 在这个技术栈上不可达**。2026-11-22 用户定口径为 ≤80MB，见下文更新节。
- 测量脚本自身成为被测对象的一部分：配置路径写错，测出来的就是另一个程序的行为。任何测量结果都要有"程序确实进入目标状态"的独立证据（这里是 `first-image` 标记与 `ws_mb` 曲线）。
- 顺带暴露一个真实缺陷：配置里没有可用图片文件夹时，程序在首帧内同步弹模态对话框，此时相框窗口可能还不可见，用户看到的是"启动了却没有窗口"。
- 每次回归测量要独占前台窗口约 40 秒（启动+静止）或 N 分钟（soak），CI 与后台代理都跑不了——资源门只能本地/人工跑。

## Update 2026-11-22: 稳定工作集预算 50MB → 80MB

本笔记的 `Problem` 节保留的是预算写下时的口径（≤50MB）。同日用户决定把 NFR-1 的稳定工作集预算改为 **≤80MB**，`spec.md`（用户故事 76、NFR-1、解码门禁）与 `.scratch/v1-exe/map.md`、票 22 已同步。

依据：空 `eframe` 窗口的稳态工作集就是 65.7MB，框架底座本身已越过 50MB；实测产品稳态 45.8–49.2MB 对 50MB 只剩不到 1MB 余量，任何图库规模或窗口尺寸变化都会破线。因此 **50MB 不可达不是实现问题，是预算与所选技术栈不匹配**，改口径而不是换渲染后端。

同时用户决定：单图 CPU 2% 边界值不再优化，轮播空闲降帧等 CPU 优化暂停。理由是本轮资源门的目标是"知道差多少并定口径"，CPU 已在边界内，继续压缩没有明确收益。
