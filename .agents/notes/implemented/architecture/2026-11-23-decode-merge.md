# Agent Note: 产品解码与验证接缝合流

Status: implemented

## Problem

产品与工单 09 验证器各自解码和缩放，绘制又单独算显示尺寸。工单 06 发现两条解码管线的正常输出相同，但验证器还把编码文件长度当成分配上限，可能拒绝解码输出完全在限内的图片。两套实现会继续让实验测到与产品不同的策略。

## Decision

- `loading` 持有图库图片解码实现与入口类型，并从 `display` 重导出 `DisplayMode`，让绘制无需反向依赖解码。正式相框使用既有 `PRODUCT_LIMITS`；`decode_validation::load_display` 只转发显式 `LoadRequest` 和阶段观察回调。`decode-validation` 保留原命令行、样本、两槽轮播与内存采样，不负责决定产品阈值。
- 不按编码长度做预检。Limits 检查源图尺寸、解码输出与缩放覆盖缓冲；拒绝原因统一随产品实现。`display` 定义唯一的比例规则：绘制保留小数，解码适应向下取整且至少为 1 像素，填充向上取整后居中裁切。保留内部适应/填充，不恢复用户设置；`display_data` 仍只管显示数据记账和决策。
- 工单 07 用 [V1 票 22/23 的完整产品实测](../../../../docs/release-measurements.md) 关闭发布门前置（峰值 130.82 MB，一小时轮播未持续增长），不再要求用原验证器重复这两项。[工单 09 的同二进制实测](../testing/2026-11-18-decode-memory-validation.md) 属于合流前的实现；没有以原验证器完成发布门最后复测的证据，两者不混用。

## Testing

- 保留工单 06 的交叉等价测试：各格式、横竖比例、不同 Limits、损坏或超限样本仍经过两个公开入口；旧编码长度差异改为两边均接受且输出一致。验证器的阶段事件仍在真实解码与释放位置发出。
- 旧实现因编码长度拒绝该回归样本，合流后两个入口都接受。Windows x64 MSVC `cargo check --all-targets`、`bash scripts/check.sh`（340 项测试）和 `decode-validation --help` 通过；不据此声称合流后完成图形内存实测。

## Alternatives considered

- **继续冻结独立实现**：能直接复现旧二进制的策略与观测结果，但会保留与产品 Limits 语义冲突的编码预检。旧版本和原始记录足以复核历史，新实验应测产品的实现。
- **同时删除内部填充**：可再减掉裁剪分支，却会改变验证器支持的模式、从样本集中移除填充覆盖边界。本次只收敛实现，不改产品完整显示整图的行为。

## Consequences

- 本笔记取代[首图切片](../feature/2026-11-20-first-image-slice.md)和[工单 09](../testing/2026-11-18-decode-memory-validation.md)中冻结、分别维护两个加载入口的处置；字体、窗口、日志和历史测量结论不改。更早的排期与原发布前置见[候选 5](../../proposed/architecture/2026-11-21-host-deepening-plan.md)。
- 新实验与产品只需改一处解码规则；要重跑合流前的内存对照，必须用旧构建，不能拿合流后的日志回填旧证据。自动化测试不替代 Windows 图形显示或工作集实测。
- 自定义相框图不是图库插画：`frame_art` 仍读取原尺寸 PNG 的透明通道做洞检测，不参与显示数据的解码缩放。
