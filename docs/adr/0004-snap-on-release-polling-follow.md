# 吸附走「松手贴合 + 轮询跟随」，不做拖动中实时磁吸

Status: accepted

多实例吸附（v0.2.0）要决定吸附在拖动的哪个时机发生、组联动靠什么机制。现行拖动是 Windows 原生模态拖动（egui `StartDrag` 后 OS 接管），且几何机有既定口径：手势进行中只记名义值、不发任何位置命令——原生手势旗标与松手重校正（含拖动回弹修复）都建立在这条口径上。决定：吸附走路线 (b)——拖动全程不干预，松手瞬间对被拖窗做吸附判定与贴合；组联动不建 IPC，每个实例进程轮询伙伴窗口位置、按几何接触派生吸附关系、各自跟随移动自己。完整口径见[多实例吸附规格](../../.scratch/multi-instance-snap/spec.md)第 5、7 节。

## Considered Options

- **(a) 拦 WM_MOVING 做拖动中实时磁吸**：最像 PotPlayer——拖着靠近就被吸住。但要给 winit 的窗口挂窗口过程子类化，这是全项目从未碰过的一层；它与原生手势旗标、模态循环结束判定的 interplay 没有把握，出问题时的故障形态（拖动卡死、位置错乱）也最难查。实时磁吸留作后续版本的升级项，届时单独 grill 与验证，不在本版下注。
- **(b) 松手贴合 + 轮询跟随**：拖动路径零改动，吸附判定挂在既有的松手时机上；联动靠枚举窗口矩形 + 接触派生，每个进程只移动自己，不需要任何跨进程协议。代价是拖动过程中没有磁吸感、跟随有约一帧量级的轮询延迟。
- **(c) 弃原生拖动、改自绘拖动**：控制权最全，吸附与联动都能在自己的拖动循环里做。但这会掀掉整套原生手势机器——回弹修复、松手重校正、几何机的名义值口径全要重做，回归风险在三条路里最高，且收益（拖动中磁吸）与 (a) 重叠。否决。

## Consequences

- 拖动过程中窗口完全自由、没有磁吸反馈；吸附只发生在松手瞬间，观感与 PotPlayer 的实时磁吸有差距——这是已知的、被接受的差距，实机验收时不要按实时磁吸的标准验本版。
- 组联动是「各自跟随」而非中心协调：跟随节奏约一帧量级，组员短暂错位可接受；实现必须防双向跟随振荡，且桌面静止时轮询不得顶起持续重绘。
- 吸附关系由几何接触派生、不落盘：本决定使「关系存储格式」问题不存在，重启恢复靠落盘几何 + 接触派生自然重建。
- 后续版本若要升级到 (a) 的实时磁吸，本 ADR 应被新的 ADR 取代（superseded），而不是直接改写本篇。
