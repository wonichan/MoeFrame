# 吸附改走 WM_MOVING 领队驱动，取代松手贴合 + 轮询跟随

Status: accepted（取代 ADR-0004）

多实例吸附（v0.2.0）的路线 (b)（松手贴合 + 轮询跟随，见 ADR-0004）在 2026-11-24 被用户实机否决：「吸附效果太差、吸附在一起后无法一起拖动」，并拍板换路线 (a)——WM_MOVING 领队驱动，照 PotPlayer 做。决定：给相框窗口挂窗口过程子类化，在 `WM_MOVING` 阶段就地改写拟拖矩形实现拖动中实时磁吸；吸附关系带方向（从属/基座，以窗口属性跨进程可读），整组联动由正在拖动的进程（领队）在拖动中用 HDWP 按同一增量原子搬走从属子树。完整口径见[多实例吸附规格](../../.scratch/multi-instance-snap/spec.md)第 15 节。

## 为什么推翻 ADR-0004

- **实机证伪（用户验收，2026-11-24）**：路线 (b) 的成品吸附手感差、贴合后拖不动整组——不是参数没调好，是机制上限被实测撞穿。
- **代码诊断确证三处硬伤**（均代码级定位，非手感猜测）：
  1. 跟随状态机用「本窗旧位置 + 伙伴新位置」的过期快照重新派生组关系，跟随者第一次追赶后间隙天然大于接触容差、自判出组，持续拖动只能「跳一次就停」；
  2. 轮询发现不对称：先启动且当时无伙伴的进程进入休眠（Dormant）后不会被后来出现的伙伴唤醒，某个方向的跟随从头不存在；
  3. 松手吸附在拖动全程零反馈，12px 落点窗口又窄，求解还按单轴类别裁决而非二维邻近评分——「吸不上、吸不准」是路线固有结果。
- **PotPlayer 调研（2026-11-24）**：其「磁性窗口」是拖动中实时磁吸、贴合后整组如一个单元移动、拖从属窗本身即把它拆走（关系带方向）；多开实例同为多进程，协调不靠 IPC——靠拖动态拦截（WM_MOVING 级别改矩形）+ 拖动态进程直接用 SetWindowPos 搬伙伴。开源世界有同构参考（CodeGuru Sticky Windows 的「Docker」模型）；本项目同栈（eframe/egui-winit）给 winit 窗口叠 SetWindowSubclass 亦有公开实战前例。当初否决 (a) 的「侵入未验证层」顾虑仍在，但现在有了必须付这个代价的实测依据。

## Considered Options

- **(a) WM_MOVING 子类化 + 领队驱动（本决定）**：拖动中实时磁吸、整组同步无轮询延迟；协调权集中在正在拖的进程，其余进程拖动中什么都不用做，Dormant/回声/双向振荡那一类跟随状态机问题整类消失。代价：子类化与 winit 自有 subclass、既有原生手势机器（回弹修复、NativeGesture 旗标、模态循环结束判定）的 interplay 只能靠 spike + 实机验证兜底，VM 内无法实证。
- **(b) 修硬伤保留路线 (b)**：修跟随组图快照、Dormant 唤醒、求解器评分化，能把上限抬到「松手吸得准、拖完后整组追过去」，但拖动中实时磁吸与全程同步在结构上仍不可达，用户已明确不接受这个上限。否决。
- **(c) 自绘拖动**：ADR-0004 已否决，理由不变（掀掉整套原生手势机器、回归风险最高），不重新考虑。

## Consequences

- 子类化只挂相框窗口、严格走 DefSubclassProc 链；与几何机分工不变——几何机在手势中照旧沉默（名义值口径、回弹修复不动），WM_MOVING 处理层只管拖动中的磁吸与整组搬运，两层不互相发命令。
- 吸附关系由「无方向接触派生」改为「带方向的属性树」：从属窗以 Win32 窗口属性记其基座 HWND，跨进程可读、不落盘、不建 IPC；接触派生只保留给存量接触（从没经拖动成关系）的临时成树与锚边变尺寸的邻居判定。ADR-0004 里「关系不落盘靠接触派生重建」的结论随之作废——重启后关系不恢复，靠落盘几何回到贴合位置、下次拖动开始时按存量接触临时成树重新联动。
- 拆组语义变精确：Shift 独走与菜单脱离在领队驱动下跨进程可保证（旧 spec 第 14 节 S1 注记的「伙伴侧不可保证」边界消失）；分离照 PotPlayer 语义——拖从属先脱离再独走，拖基座带整棵子树。
- 坐标纪律收紧：WM_MOVING 路径全程物理像素（lParam、GetWindowRect、工作区 rcWork 同源），本窗矩形一律走自家 HWND 的 GetWindowRect，根除旧诊断中逻辑/物理混源的嫌疑。
- 本 ADR 取代 ADR-0004；0004 原文保留作决策史。
