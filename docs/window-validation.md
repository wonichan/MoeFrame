# 08 无边框窗口验证


**这是独立验证工具，不是正式相框。用户已在本机实际操作并确认通过，08 的正式窗口实现门禁（本机部分）解除。**

本机实际为 Windows 11 x64 Build **26200**、系统缩放 150%，不是票内计划的 Build 26100。Win10、Build 26100、100% 缩放与混合 DPI 双屏仍为未验证，不能沿用本机结果。

## 构建与启动

在仓库根目录运行（PowerShell）：

```powershell
cargo build --release --bin window-validation --locked
.\target\release\window-validation.exe
```

- 编译最低版本以 `Cargo.toml` 的 `rust-version = "1.95"` 为准；实际编译器写入日志。
- 验证窗口初始为 480×320 逻辑点，最小为 120×120；不锁定比例。
- 内容区左键按下即请求原生移动；距客户区内边缘不足 8 逻辑点的边带请求缩放，四角优先。150% 时 8 逻辑点约为 12 物理像素。
- `F9`：记录手动快照。`F10`：验证专用最大化/还原。`Esc`：退出。
- 不加载用户图片，不做轮播、托盘、设置恢复或正式产品的最大化按钮。

## 操作前

1. 保留当前常用应用在前台，再启动验证窗口，观察是否被抢焦点。不要先点击验证窗口再判断创建焦点。
2. 记录 `winver` 中的实际系统版本、显示设置中的缩放、显示器数量，以及窗口显示的 DPI。
3. 记下本次日志文件名；每次启动使用独立文件。首次按 F9 前需要主动聚焦验证窗口。
4. 以下每项亲自操作后填写结果。请求计数、截图、编译通过或日志读数都不是人工通过。

## 日志与结果回传

日志目录：`%APPDATA%\MoeFrame\window-validation\`，文件名为 `validation-时间戳-进程号-序号.log`。

记录包括：实际 Windows 内核 Build、编译器/Cargo、目标与构建类型、Git revision 与 dirty、锁定依赖版本；原生 DPI、缩放、逻辑客户区、winit 物理客户区、Win32 原始客户区和窗口坐标；最大化、焦点、前台与置顶观测；按下事件及移动/缩放请求。

- `physical_client` 来自 winit `PhysicalSize`；`win32_client` 是原始 `GetClientRect` 读数。`system_logical_client` 是物理尺寸除原生缩放的**换算值**，不是另一份实测。
- `None` 表示未知，不表示零或通过；`verdict=unverified` 故意不自动升级为通过。
- 120 逻辑点在 100%/150% 下通常分别对应 120/180 物理像素；这些是核对用的换算，不是本次实测记录。
- 窗口观测每 250ms 刷新并在变化时落盘，不是完整 Win32 消息追踪。输入请求只说明命令已排队。winit 0.30.13 对无装饰窗口仍保留 `WS_CAPTION`/`WS_THICKFRAME` 样式位，因此不能用样式位判断「无边框」，该项只能由实际操作时的视觉确认；`keyboard_focus` 只在本窗口为前台时判定，其余记为 `None`。
- 出现测量未知、日志错误或无法启动时停止验收。查看最新日志的 `backend_error`；若日志目录本身不可写，检查 APPDATA 和目录权限，保留运行错误，不把没有日志当通过。

## 实测记录（2026-11-17，用户操作）

- 系统：Windows NT 10.0.26200 x86_64；单屏、DPI 144、系统缩放 150%、egui ppp 1.5；DPI 感知为 per-monitor v2。
- 构建：release，rustc/cargo 1.99.1，target x86_64-pc-windows-msvc，revision `b67eca4…`、dirty=true（提交前工作区）；eframe/egui/egui-winit 0.37.0、winit 0.30.13、raw-window-handle 0.6.2。
- 初始客户区 480×320 逻辑点 = 720×480 物理像素；winit `PhysicalSize` 与 `GetClientRect` 读数一致。
- 创建时前台与 winit 焦点仍属原应用（`foreground=false`、`winit_focus=false`），`topmost=false`；窗口内容显示四边无系统标题栏与边框。
- 最大化 2560×1392 逻辑点 / 3840×2088 物理像素；F10 还原后回到 720×480，随后仍能继续移动与缩放。
- 缩放请求记录到 South、SouthEast 等方向，客户区随之变为 188.0×183.3 逻辑点 / 282×275 物理像素；同时有多次 MoveRequested 与窗口坐标变化。
- 退出记录 `CloseRequested` 与 `exit`；三次启动各生成独立日志文件，未互相覆盖。
- 日志：`validation-1794935202437290100-10416-0.log`（另两次启动为 `…19000-0.log`、`…21432-0.log`）。

日志只证明命令已排队且原生状态随之变化；拖动手感、边缘是否误触移动、系统阴影是否残留等由用户实际操作确认。120×120 精确下限未出现在日志快照中。

失败时先核对按下时机、输入位置、原生/egui 最大化状态、DPI 与焦点，不自行切换 GUI 框架。确认调用仍不能满足要求后另开备选票。**用户明确确认本机操作后，才能完成 08 并解除对应正式窗口实现的阻塞；这不代表 Win10 或其他 DPI/双屏已通过。**

## 实施证据与边界

- 自动化覆盖 egui 输入到视口命令，以及真实文件日志两处已确认接缝；不测试私有命中函数，不 mock Windows 通过。
- 17 项自动测试（输入入口 12 项、真实文件日志 5 项）、`cargo check --all-targets --locked`、`cargo fmt --all -- --check` 与 release 构建均通过；release 程序已在本机启动并写入上述日志。这些仍不能替代上表的用户操作确认。
