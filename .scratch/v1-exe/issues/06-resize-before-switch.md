# 边缘缩放先验证

Label: wayfinder:grilling
Type: grilling
Status: resolved

## Question

eframe 0.37.0 在 Windows 上，无边框、客户区拖动、最小尺寸、默认不置顶可以做到。只靠 `with_resizable(true)` 不能拖边缘或四角。`ViewportCommand::BeginResize` 有实现，这台机器没跑过，不能记成做得到。

Rust + eframe/egui 已经钉死。要决定的只是：在打开这个选择之前，是否先在这台 Windows 10/11 上验证 `BeginResize`。验证通过就不换框架。验证失败，才另开一张票问备选界面方案。

不要在这张票里选备选框架，也不要现在写窗口代码。

## Answer

先在本机做独立最小验证，通过后才继续正式窗口实现。通过就沿用 Rust + eframe/egui；失败先排查调用方式，确认仍不能满足要求后，再另开票讨论备选界面方案，不直接换框架。

本票关闭的是验证路线的决定，不是实机验证。本轮只记录决定，不写窗口代码，不选择备选框架。[04 的研究结论](04-borderless-window.md)及其已关闭状态保持不变。

### 验证范围与通过条件

验证程序只验证窗口能力，不做完整相框：

- 无标题栏、无系统边框。
- 四边、四角都能反复放大和缩小，最小尺寸为 120×120 逻辑尺寸。
- 内容区可拖动窗口，边缘缩放不误触发移动。
- 默认不置顶，创建时不抢焦点。
- 记录当前 DPI 和物理客户区尺寸。
- 最大化时不发起边缘缩放；恢复普通大小后，移动和八方向缩放仍可用。验证这条不等于给正式产品增加最大化按钮。

图片解码、轮播、托盘、配置恢复、宽高比锁定不加入本次最小验证，留给正式实现验收。

### 覆盖范围与结果确认

- 先测当前本机：Windows 11 x64，Build 26100。
- 本机通过只作为继续实现的门槛，不代表 Windows 10/11 已全部兼容。Windows 10、混合 DPI 双屏等未测环境明确保留为未验证，不降低最终验收要求。
- Agent 准备验证程序、操作清单和诊断日志；用户在本机实际拖动、缩放并反馈，确认结果。
- 编译成功、截图正常、API 返回成功都不能替代实际操作通过。未实际操作的项目记为未验证。

### 依据与取舍

- [egui 0.37.0 的 BeginResize 文档](https://docs.rs/egui/0.37.0/egui/viewport/enum.ViewportCommand.html#variant.BeginResize)说明该命令发起左键缩放，如果不是紧接左键按下调用，就不能保证生效。排查调用方式时要核对这一前提，不能把错误调用判成框架不支持。
- [winit #4821](https://github.com/rust-windowing/winit/issues/4821)报告：在最大化窗口上调用 `drag_resize_window` 后，恢复窗口的后续移动、缩放可能失效，调用仍返回 `Ok(())`。这是上游报告，不是本机复现结果，因此要验证最大化后恢复的路径。
- 不等完整相框实现后才验证：先隔离窗口风险，避免把验证程序做成半个产品。
- 不在本机验证前更换框架：API 存在不等于实机通过，尚未验证也不等于做不到。
- 不要求本步骤找齐所有目标环境：先确认本机能继续做，但不把局部通过写成完整兼容性验收。
