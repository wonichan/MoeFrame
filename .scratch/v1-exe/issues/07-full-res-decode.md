# 全分辨率解码

Label: wayfinder:grilling
Type: grilling
Status: resolved

## Question

image 0.25.10 不能在 jpeg、png、webp、bmp 的解码过程中降到窗口物理像素。只留当前图和下一张，也不能把解码峰值变成两张小图。1080p、2K、4K、100MP 的实测峰值字节数未知，所以还不能说已经守不住 50MB，也不能说 100MP 一定撑爆。

要决定：V1 是否仍用 image 做全分辨率解码，并用 Limits 拒绝过大的输出，而不是现在换解码器。若否，下一张票才选备选路径。

不要在这张票里选备选解码器。

## Answer

用户已确认：V1 暂定保留 image 全分辨率解码，缩到显示所需尺寸后释放整图，并用 Limits 拒绝过大输出；先做独立最小验证，通过后才进入正式实现。不在本票选择备选解码器。

本票的 `Status: resolved` 只表示路线决定已确认，不代表验证已执行或解码方案已验收通过。

### 验收边界

- 允许短暂持有全分辨率解码数据，随后缩到窗口物理像素尺寸（填充按覆盖尺寸）并释放整图；长期只保留当前图和下一张的显示数据，不把解码峰值说成两张小图。
- 合法但超过安全限制的超大图可以拒绝，记录路径和超限原因后跳到下一张，不再要求 100MP 图片一定显示。普通 1080p、2K、4K 图片仍须正常显示，不能靠大量拒绝普通图片满足内存指标。
- 默认 480×320 窗口下，后台解码、缩放及下一张预加载完成后的稳定工作集须 ≤50MB；连续轮播 1 小时无持续增长的要求不变。
- 解码瞬时峰值单独测量并确定可接受边界，不自动按稳定工作集的 50MB 判定，也不允许无限上涨。

### 验证路线与后续确认

- 先做独立最小验证，测普通图片与超大图的稳定工作集、瞬时峰值和拒绝行为，通过后才进入正式实现。
- 瞬时峰值上限和具体 Limits 阈值不在本轮凭空定数值，也不把库的默认值当作产品安全线。先测量，再提出限制建议，由用户确认后确定；这两项是验证阶段必须关闭的事项。
- 验证失败先排查缓冲重复、释放时机和限制设置；确认这条路线仍不能达标后，再另开票讨论备选解码器，不直接换方案。

### 依据与取舍

- [前序研究](../research/downsample-decode.md)已确认 image 0.25.10 不能按窗口目标尺寸边解码边缩小，但还没有这几档图片的实测峰值。未知不能当作失败，也不能当作通过，因此先隔离风险验证，而不是现在更换解码器。
- [Limits 官方文档](https://docs.rs/image/0.25.10/image/struct.Limits.html)将 `max_alloc` 标为非严格限制，不能把它当作整个进程工作集的硬上限。解码输出限制与实际内存验收必须分开。
- 不要求所有 100MP 图片都显示：代价是某些合法图片会被跳过，收益是允许 V1 优先守住轻量与持续运行的目标。普通图片的显示要求和损坏文件不崩溃的要求不降低。
- 不把 50MB 强加到每个解码瞬间：保留稳定工作集指标，同时把瞬时峰值边界列为待实测、待用户确认的明确门槛，不能悄悄放宽验收。
