# 22: 完整程序的轻量 release 达标

**What to build:** 产出具备全部必需功能、能轻量常驻的 release 程序，并用完整程序的真实测量证明内存、CPU、启动和体积满足要求，而非沿用独立验证程序的结果。

**Blocked by:** [15: 点击、双击、拖动分界与当前图操作](15-gesture-image-actions.md)、[19: 路径与秒数编辑：草稿、提交和校验](19-settings-drafts.md)、[20: 窗口位置恢复、宽高比锁定与多屏显示](20-window-geometry-dpi.md)、[21: 开机自启与失败回滚](21-autostart.md)。

**Status:** ready-for-agent

## Acceptance criteria

- [ ] 对包含全部必需功能的程序生成实际 Windows x86_64 release 构建，启用 strip 与 LTO；交付构建不依赖开发环境或 WebView，不用 debug 二进制替代。
- [x] 默认 480×320 窗口、普通图片解码缩放及下一张预加载完成后，稳定工作集 ≤80MB；全程序连续轮播 1 小时无持续增长。（2026-11-22 用户单独验证：1 小时轮播无持续增长，通过）
- [ ] 瞬时峰值在 [09](09-decode-memory-validation.md)中用户已确认的边界内，图片拒绝阈值与确认值一致；分别记录峰值和稳定工作集，不以 Limits 充当整个进程内存硬上限。
- [ ] 普通 1080p、2K、4K 图片仍正常显示；超限大图可跳过并记录路径、原因。加载和缩放不阻塞相框操作，不能靠大幅拒绝普通图片满足指标。
- [ ] 静止显示时平均单核 CPU <1%；记录测量口径和时间，动画、解码瞬间短时升高与静止结果分开报告。
- [ ] 实际 release 程序体积 ≤15MB；普通图片冷启动到首张图显示 <1 秒，不能忽略扫描耗时。超大图首次解码的合理例外单独列明，不笼统扩大例外范围。
- [ ] 10,000 张图库的扫描和启动保持可操作，只枚举路径、不全量解码；不引入文件监听、定时重扫或图库全量像素缓存。
- [ ] 完整程序长期只保留当前图与下一张显示数据；按窗口物理像素需求缩放、填充按覆盖尺寸，整图及时释放，动画结束释放旧纹理。结合资源生命周期检查与实测证明，不只给理论字节数。
- [ ] 程序不联网、不遥测、不上传、不投放广告，不为满足启动或体积目标增添外部运行服务或额外下载步骤。
- [ ] 记录构建、系统、显示器、DPI、样本和测量步骤，以任务管理器读数及持续观察核对资源指标，留存可复测证据；最小验证通过不能代替本次结果。
- [ ] 为资源问题所作修改保持外部行为，并运行全部核心及应用行为测试；新增回归用例落在原确认接缝，不为优化扩大私有接口或绑定 GUI 帧数。
- [ ] 任一必需预算未达标，或峰值阈值尚未确认，保持本票未完成并记录具体缺口；先沿既定路线排查，不自行更换 GUI 框架或解码器。

### 更正：之前的启动与工作集数字全部作废（2026-11-22）

`scripts/measure-release.ps1` 把临时配置写在 `<tmp-appdata>\config.toml`，而程序读的是 `<tmp-appdata>\MoeFrame\config.toml`。于是**每次测量都跑在"没有配置好图片文件夹"的状态**：首帧同步弹出文件夹选择对话框（`Effect::PickFolder` → `rfd`），主线程被模态对话框挡住，日志里因此出现 1–5s 乃至 45s 的"停顿"，工作集也因对话框拉起的 COM/Shell 多出约 75MB。

脚本已修（配置改写到 `MoeFrame\config.toml`）。修正后的同一台机器、同一个 exe：

| 项 | 旧（污染） | 新（修正） | 目标 |
| --- | --- | --- | --- |
| 冷启动到首张图 | 2833 / 5207ms | **282ms** | <1s ✓ |
| 静止稳态工作集 | 151.68 / 156.66MB | **67.79MB** | ≤80MB ✅ |
| 静止平均 CPU | 0.48% / 5.47% | **0%** | <1% ✓ |
| 体积 | 7.48MB | 7.48MB | ≤15MB ✓ |

所以启动达标、CPU 达标，只剩工作集一项。而空 eframe 窗口（同一份依赖、同一种 Glow 渲染器、480×320 无边框）的稳态工作集就有 **65.7MB** → 框架底座本身已越过 50MB 预算，本项目的自有状态只占约 2–3MB。这一项不是"优化代码"能解决的，需要先定口径。

顺带记一个真实缺陷：配置里没有可用的图片文件夹时，程序在首帧内同步弹模态对话框，此时相框窗口可能还不可见，用户看到的是"启动了但什么都没出现"。应改为在首帧之后弹、或先显示窗口再弹。

### 工作集归因（2026-11-22）

进程内 `[startup]` 标记自带 `ws_mb`（`GetProcessMemoryInfo`），一次启动即得各阶段工作集：`launch` 8MB → `app-created` 55MB → `first-frame` 57MB → 描一张小图后稳定 64–68MB。也就是说 55MB 在窗口 + GL 上下文 + egui 上下文建好后就已经在了，产物侧只再加 2–3MB。

对照实验（`target/memprobe`，同一 `Cargo.toml` 依赖集、同一个 Glow 渲染器）：空窗口稳态 **65.7MB WS / 63.5MB private**，与本程序相差在噪声内 → 结论同上：工作集由框架底座决定。

已定（2026-11-22，用户决定）：稳定工作集预算 **≤80MB**。理由：空 eframe 窗口底座已占 65.7MB，50MB 装不下框架本身；实测 45.8–49.2MB 相对 50MB 只剩不到 1MB 余量，任何图库或窗口尺寸变化都会破线。换渲染后端/自绘托盘以压到 50MB 的方案不再推进，CPU 优化同样暂停。

### 交付构建验收（2026-11-22，`161bb18` + 图标与 PR #1）

`scripts/measure-release.ps1 -SkipSoak`，同一 exe（`target/release/MoeFrame.exe`，7.86MB）跑两次，只换图库：

| 图库 | 冷启动到首图 | 静止稳态工作集（5–30s 均值） | 静止平均 CPU |
|---|---|---|---|
| 13 张样例（含 1080p/2K/4K/100MP 级） | **279ms** | **72.28MB**（72.27–72.29） | 0.05% |
| 单张 512×512 | **266ms** | **71.00MB**（70.99–71.00） | 0.05% |

判定：启动、工作集、CPU 三项对 ≤80MB 预算全部通过，余量 7.7MB。图库从 1 张换成 13 张大图只多 1.28MB，再次确认稳定工作集与图片尺寸无关。

注意采样口径：此处的"稳态工作集"是首图出现后 5–30s 的均值；`[startup] first-image` 标记写的 46–52MB 是首图那一刻的值。两者不可混用——首图之后才发生下一张预加载与纹理驻留。
